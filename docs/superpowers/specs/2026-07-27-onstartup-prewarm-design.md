# ブラウザ起動時の事前起動（onStartup prewarm）

2026-07-27

前提: [ネイティブホストの事前起動（prewarm）](2026-07-26-ime-host-prewarm-design.md)

## 解決する問題

既存の prewarm は「属性を含む文書を開いた時点」でホストを温める。対象欄が
`autofocus` されているページでは、**フォーカスと prewarm が同じ瞬間に起きる**ため、
利得がゼロになる。

そのときユーザーに起きることは、単なる遅れではない。`focusin`
（`extension/content.js:93`）から `acquire`（`extension/background.js:81`）を経て
ホストが立つまで 1.2 秒あるので、その間まちがったモードで打ち、**打鍵の途中で
IME が切り替わる**。`data-ime-mode="inactive"` を指定した ID 欄なら、その 1.2 秒は
日本語入力のままになる。ログインフォームはこの拡張機能の本命の用途で、しかも
`autofocus` を持つことが多い。

既存 prewarm の設計内では詰められない。属性の有無は DOM を見ないと分からず、
DOM ができる時刻と `autofocus` が発火する時刻は同じだからである。

## 方針

**Edge の起動時にホストを温める。** ページより前なので、どのサイトのどんな
フォームでも初回フォーカスが間に合う。

判定材料を持たない場所で温めるため、条件は付けない。この拡張機能が入っている
こと自体を「使う意思がある」というシグナルとして扱う。ネイティブホストの登録
（`host/install.ps1` の実行とレジストリ書き込み）という手作業を経ないと動かない
以上、入っているのに使わない人はほぼいない。

## 設計

### extension/background.js（1 行の追加、コメント込みで 3 行）

```js
// Edge の起動時点で温める。属性付きページを開いた時では、autofocus された
// 対象欄には間に合わない（フォーカスと prewarm が同じ瞬間に起きる）。
chrome.runtime.onStartup.addListener(() => enqueue(() => call({ cmd: 'ping' })));
```

- 置き場所はファイル末尾、`setInterval` の keepalive（`background.js:116`）の隣。
- 既存の直列キュー（`background.js:89`）に乗せるので、温めと適用の順序は保たれる。
- `connect()` の `if (port) return port;`（`background.js:19`）により、その後の
  ページ単位 prewarm はプロセスを増やさない。
- **リスナー登録はトップレベルに置く。** `onMessage`（`background.js:94`）や
  `setInterval`（`background.js:116`）と同じ場所である。サービスワーカーは
  イベントで起き直すため、非同期の内側で登録するとイベントを取りこぼす。
- **トップレベルでの即時 `call()` にはしない。** サービスワーカーは頻繁に起き直る
  ので、それではポートが切れるたびに、誰も要求していないのにプロセスが立つ。
  温めるのは「ブラウザが起動した」という 1 度きりの合図に対してだけである。

`ping` を選ぶ理由は既存 spec と同じ。ホストは `Invoke-ImeRequest` の冒頭
（`host/ime-host.ps1:171`）でこれを即返し、**ウィンドウ解決も IME 操作も一切
しない**。`$script:lastChange` も設定されないので、温めただけでポートが切れても
復帰処理は走らない。

### extension/content.js（変更なし）

既存のページ単位 prewarm（`content.js:32-48`）はそのまま残す。`onStartup` が
発火しない経路 — ポートが切れたあと、拡張機能の再読み込み後 — の温め直しは
これだけが担う。

### extension/manifest.json（変更なし）

`matches` は `<all_urls>` のまま。

検討の過程で `matches` を対象サイトに絞る案を出したが、**ホストの常駐には効かない**。
`matches` が制御するのは content script の注入範囲だけで、`onStartup` はサイトと
無関係に発火する。絞って得られるのは content.js を `document_start` で単純化できる
ことだけで、その代わりに配布ごとの manifest 書き換えと、`test/test.html` を
開くための `file:///*` と「ファイルの URL へのアクセスを許可する」トグルを背負う。
割に合わない。

## 放棄する不変条件

既存 spec 「方針」節と README「既知の制約」が明示していた

> 属性を使っていないページでは PowerShell を 1 度も起動しない

は成立しなくなる。この拡張機能を入れている限り、Edge の起動時にホストが立つ。

黙って変えてよい性質ではないので、README の記述を書き換えることを本変更に含める
（下記「README の更新」）。

## 受け入れる代償

対象の欄を 1 度も触らない日でも、Edge を開いている間ずっとホストが常駐する。
実測（起動して ping を往復させ、2 秒後）:

| | |
|---|---|
| WorkingSet（物理） | 83.8 MB |
| PrivateMemory（コミット） | 58.1 MB |
| ping 5 往復後の合計 CPU 時間 | 2.06 秒（ほぼ全部が起動時の `Add-Type`。ping 自体は 0 に近い） |

CPU は無視できる。メモリは Edge のセッション中ずっと払う。

ポートが閉じないのは既存の性質である。`background.js:116` の 20 秒 keepalive には
ポートを閉じる経路がなく、一度温まればセッション中は常駐し続けていた。本変更は
その開始時刻を「最初に属性付きページを開いた時」から「Edge の起動時」へ動かす。

## テスト

`test/content.test.js` の `loadBackground()`（`test/content.test.js:67`）の
`chrome.runtime` スタブに `onStartup` を足し、登録されたハンドラを返す:

```js
onStartup: { addListener: (fn) => { startupHandler = fn; } },
```

追加するアサーション:

- **`onStartup` が発火するまで `connectNative` を呼ばない。** 既存の
  `background 読み込みだけでは connectNative を呼ばない`（`test/content.test.js:350`）
  の趣旨をそのまま守る。ここをトップレベルの即時実行に書き換えると、サービス
  ワーカーが起きるたびにプロセスが生まれる。このアサーションだけがそれを止める。
- `onStartup` の発火で `connectNative` がちょうど 1 回呼ばれ、`ping` が 1 通だけ飛ぶ。
- `onStartup` の後にページ単位 prewarm が来てもプロセスが増えない
  （`connectStats.count` が 1 のまま）。`connect()` のガードが onStartup 経由でも
  効いていることの確認。
- `onStartup` が `set` を送らない。IME に触らないことの確認で、既存の prewarm の
  テスト（`test/content.test.js:398`）と同型。

`test/host.test.ps1` と `test/host.e2e.ps1` は変更しない。ホスト側は何も変わらない。

## 実測で確かめること

`host/debug.on` を置き、`host/debug.log` のタイムスタンプで確認する。

1. **`onStartup` の温めが、セッション復元のタブの読み込みより先に終わるか。**
   Edge 起動時はサービスワーカーの起動と最初のタブの読み込みが並走する。1.2 秒の
   先行を取れなければ本変更の主目的が達成できないので、ここは実機で確認するまで
   「入った」と言えない。
2. **Edge の「起動ブースト」下での挙動。** ウィンドウを全部閉じてもブラウザ
   プロセスが残る構成では、再びウィンドウを開いても `onStartup` は発火しない
   可能性がある。その場合はポートもサービスワーカーも生きているはずで実害はない、
   という想定の裏取り。
3. **スリープ復帰後にホストが生きているか。** 死んでいれば次のページ遷移の
   prewarm が拾う（既存経路）ので機能上は問題ないが、どちらなのかは知っておく。

## README の更新

- 「既知の制約」の「ホストプロセスは Edge の起動時ではなく、**属性を含むページを
  開いた時**に起動します」を、起動時に立つ、へ書き換える。続く「属性を使って
  いないページしか見ない間は、PowerShell は 1 度も起動しません」は成立しなくなる
  ので削除する。
- 「事前起動（prewarm）」の節に onStartup の段を足す。**なぜ文書より前でなければ
  ならないか**（`autofocus` された対象欄では、属性を見てから温めるのでは同時に
  なる）を理由として書く。
- 上の常駐コスト（83.8 MB、Edge を開いている間ずっと）を書く。入れれば常に払う
  性質なので、導入判断の材料として隠さない。
- 同じ「既知の制約」にある「その瞬間にコンソールウィンドウが一瞬見えることが
  あります」は、実機では出ていないとの報告がある。この機会に確かめ、出ないなら
  記述を落とす。

## やらないこと

- **`chrome.storage.local` の sticky フラグで温める条件を絞る。** 守れるのは
  「入れたが属性に一度も出会わない」人だけで、一度当たれば以後ずっと真になるため
  上記の代償は消えない。ネイティブホスト登録の手作業を経て入れている以上、守る
  相手がほぼいない。
- **`chrome.runtime.onInstalled` でも温める。** README の導入手順が「Edge を完全に
  終了して起動し直す」なので `onStartup` が拾う。開発中の再読み込みはページ単位
  prewarm が拾う。必要になってから足す。
- **`MutationObserver` で属性の後付けを検知して prewarm。** `onStartup` で温まって
  いれば、後付けされた欄への初回フォーカスも ~1ms で済む。
- **`background.js:54` の 3 秒タイムアウトの見直し。** コールドの 1.2 秒に対して
  余裕が 1.8 秒しかなく、超えると 1 通目が捨てられたまま content.js 側は適用済みと
  記憶する既知の隙間である。`onStartup` はこの経路を誰も待っていない起動時へ移す
  ため露出は減るが、手当てそのものは別の変更になる（既存 spec の同項目と同じ扱い）。
- **ネイティブホストの exe 化。** 起動 1.2 秒（`powershell.exe` の 650ms と
  `Add-Type` の 350ms）を ~40ms にできることは計測で確かめてあるが、ホストを C# へ
  書き直す規模になる。prewarm が体感を隠している間は見合わない。ブラウザからの
  PowerShell 起動がポリシーで塞がれる配布先が出てきた時点で再検討する。その場合の
  形はインストール時コンパイルではなく、署名済みの事前ビルドバイナリになる
  （インストール時コンパイルはマシンごとに異なるハッシュを生み、普及度が永久に
  ゼロのままなので、AV/ASR の判定に対して最悪の入力になる）。
