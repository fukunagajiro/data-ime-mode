# ネイティブホストの事前起動（prewarm）

2026-07-26

## 解決する問題

制御対象の欄へ初めてフォーカスしたとき、IME が切り替わるまで体感で待たされる。

原因は、ネイティブホストの PowerShell プロセスがその瞬間に起動することにある。
`background.js` の `connect()` は遅延実行で、最初の要求が来たときに初めて
`connectNative` する。

実測（同一環境で 3 回ずつ）:

| 区間 | 時間 |
|---|---|
| ホスト起動 → 最初の応答（コールド） | 1,220 – 1,310 ms |
| 2 回目以降（ポート確立後） | 0.3 – 2.0 ms |
| 内訳: `powershell.exe` の起動だけ | 637 – 762 ms |
| 内訳: `Add-Type`（C# の実行時コンパイル）だけ | 340 – 468 ms |

体感の遅れはほぼ全部この 1.2 秒である。IME 操作そのものは速く、診断ログでも
`WM_IME_CONTROL` の往復は 0–9ms だった。

## 方針

**属性を含む文書を開いた時点でホストを起動しておく。** フォーカスより前に
1.2 秒を払い終えるので、初回フォーカスの待ちが消える。

起動条件を「初めて対象欄にフォーカスした時」から「属性を含むページを開いた時」へ
前へずらす。フォームのあるページを開くことは、まもなく入力することとほぼ同じなので
妥当と判断した。**属性を使っていないページでは 1 度も起動しない**という性質は
維持する。これが崩れると、この拡張機能を入れているだけであらゆるページで
PowerShell が常駐することになる。

## 設計

### content.js（約 10 行の追加）

- content script は `document_start` で走るので DOM がまだ無い。
  `document.readyState === 'loading'` なら `DOMContentLoaded` を待ち、
  そうでなければ即実行する（他の実行タイミングでも壊れないように）。
- `document.querySelector('[data-ime-mode]')` が当たった文書だけ、prewarm を
  1 通送る。文書あたり 1 回だけ（モジュールスコープのフラグ）。
- 判定は**属性の存在だけ**で、値が既知のモードかは見ない。`data-ime-mode="disabled"`
  のような未知の値しか無いページでも prewarm は走り、実際の適用は起きない。値は
  後から変わりうるうえ、`modeOf()` の判定を 2 か所に持つ方が壊れやすいため。
- **`currentMode` には触らない。** prewarm は「適用」ではないので、失敗しても
  `forget()` を呼ばず、送信結果は捨てる。ここを混ぜると重複排除の状態が壊れる。

### background.js（約 4 行の追加）

- `msg.prewarm` を `spec` の判定より**前に**見て、`enqueue(() => call({ cmd: 'ping' }))`
  して return する。
- **順序が重要**: 今の実装は `msg.spec ? acquire(msg.spec) : release()` なので、
  `spec` を持たないメッセージは「解放」として扱われる。prewarm を素朴に足すと
  ページを開くたびに release が走る。`saved` が無ければ実害は出ないが、意図と
  異なる経路なので先に分岐させる。
- 既存の直列キューに乗せるので、prewarm と適用の順序は保たれる。
- `connect()` の `if (port) return port;` により、2 通目以降はプロセスを増やさない。

### なぜ `ping` か

ホストは `Invoke-ImeRequest` の冒頭（`host/ime-host.ps1:171`）で `ping` を即返し、
**ウィンドウ解決も IME 操作も一切しない**。`$script:lastChange` も設定されないため、
prewarm だけしてポートが切れても復帰処理は走らない。

採らなかった案:

- `connect()` だけ呼んでポートを開く（ping を送らない）— プロセスは起動するが
  生存確認ができず、失敗が黙って消える。1 往復 1ms なので節約する意味がない。
- background 側で属性を判定する — content script が既に知っている情報を渡し直す
  だけで、間接化する利得がない。

## ページ遷移時の振る舞い

サーバーレンダリングのアプリ（Spring MVC など）では遷移ごとに content script が
読み込まれ、prewarm も毎回走る。ただしポートを持つのはサービスワーカーなので、
**プロセスが起動するのは最初の 1 回だけ**で、2 回目以降は ping の往復（~1ms）で終わる。

サービスワーカーが破棄されてポートが切れた場合、次のページ遷移が prewarm を
やり直すため、ユーザーがフォーカスするより前に温め直せる。現状の実装では
破棄後の初回フォーカスがまた 1.2 秒待ちになるので、この点は改善になる。

`all_frames: true` なのでフレームごとに prewarm が飛ぶが、属性を持つフレームだけに
限られ、どれも既存ポートへの ping なので害はない。

## テスト

`content.test.js` に追加:

- 属性のある文書は prewarm を 1 通送る
- 属性が無い文書は何も送らない
- prewarm の後の `focusin` が正しく適用される（`currentMode` を汚していない）
- prewarm が reject しても以後の適用に影響しない
- background が prewarm を `ping` に変換し、`set` を送らない

スタブに `readyState` と `querySelector` を足す必要がある。

`host.e2e.ps1` に追加:

- **ping だけ送ってポートを閉じても IME は変わらない** — `lastChange` が設定されて
  いないことの実機での裏取り。

## README の更新

- 「ホストプロセスは……初めて制御対象の欄にフォーカスした時に起動します」を、
  属性を含むページを開いた時点に修正する。属性を使っていないページでは 1 度も
  起動しない性質は維持されるので、その記述は残す。
- 上記の実測値を、なぜ prewarm するのかの根拠として書く。

## やらないこと

- **動的に追加された欄のための再 prewarm**（`MutationObserver`）。必要になってから足す。

  遅延を払う条件は狭い。ポートを持つのはサービスワーカーで、`port` はモジュール
  スコープの単一変数なので**全タブ・全フレームで共有される**。したがって、
  そのブラウザセッションで属性を含むページを 1 度でも開いていれば、動的に
  追加された欄への初回フォーカスも ~1ms で済む。1.2 秒を払うのは「読み込み時点で
  属性を持つ要素が無い文書」かつ「まだホストが立っていない（またはサービス
  ワーカーが破棄されてポートが切れた）」場合だけである。
- **`Add-Type` の 350ms と PowerShell 起動の 650ms の削減**。prewarm が入れば
  体感には出ない。消すには C# の exe をインストール時に `csc.exe`
  （`C:\Windows\Microsoft.NET\Framework64\v4.0.30319\csc.exe`、.NET Framework 4 同梱）
  でコンパイルする案があるが、ホストを書き直す規模になるため別途判断する。
- **`background.js:54` の 3 秒タイムアウトの見直し**。コールド 1.2 秒に対して余裕は
  1.8 秒しかなく、超えると 1 通目が捨てられたまま content.js 側は適用済みと記憶する。
  prewarm はこの経路を通りにくくするが、根本の手当ては別の変更になる。
